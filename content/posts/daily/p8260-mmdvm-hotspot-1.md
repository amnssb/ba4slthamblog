# 折腾吃灰的 P8260 和三无 MMDVM 热点板（一）：看似打通，其实才刚开始

几个月前脑子一热收了台摩托罗拉 P8260，顺手又图便宜买了块啥文档都没给的 MMDVM 热点板，背面就光秃秃印着一行 `MMDVM-HS-Pi-Hat`。买回来新鲜劲一过就扔抽屉吃灰了，这两天才想起来拿出来鼓捣一下。

原以为就是接上线、编个软件、写个频就能通联的事，结果前前后后折腾了两天，踩的坑一个比一个离谱。写到这篇结尾的时候，表面上看好像全链路都跑通了，甚至连 9990 鹦鹉回放都听见自己声音了——但实际一用才发现根本没法正常通联，动不动就吞首包头，属于是以为快大结局了，其实正片才刚开始。

先说一声，这次软件层面的活——翻网表、编译、改配置、扒固件源码、看日志——基本没怎么自己手敲，全丢给 Agent 在调。一开始用的是 DeepSeek-Harness（dsh），但它跑在容器里权限不够，干啥都卡手，后面直接换成了 oh-my-pi（omp）。模型换着用了 DeepSeek V4.1 Flash、GLM-5.3-Flash 和 GPT-6.1 Sol，我本人基本就负责在旁边插拔杜邦线、断电上电、拿手台按 PTT。

## 没树莓派，拿 CH340 硬接

板子是经典的 STM32F103 + ADF7021 加一颗 14.7456MHz 温补晶振，正面带块 0.96 寸 OLED，底下是一排树莓派 40Pin 排针。但我手上根本没有树莓派，也不打算为了个热点专门去买一块。主力机跑的是 Arch Linux，手边正好有块几块钱的 CH340G USB 转串口，想着这板子本来也是走串口通信的，直接接电脑上跑原生的 `MMDVMHost` 算了。

因为卖家啥资料都没给，最开始我凭直觉把 CH340 的 5V 插到了排针 2 脚。上电之后屏幕死黑、串口没反应，拿表量 TX 脚才 0.08V，当时差点以为买到块坏板子。

让 Agent 去 GitHub 翻了开源原版 `MMDVM_HS_Hat`（r1.6）的网表才看明白：板子上的 5V（2、4 脚）只通向 Nextion 串口屏接口，跟主板压根没关系；STM32 和 ADF7021 是直接从 1 脚和 17 脚吃 3.3V 的，板上根本没做 5V 转 3.3V 降压。串口对应排针 8 脚（STM32 RX）和 10 脚（STM32 TX）。

按网表重新接好（CH340 的 3V3 接 1 脚、GND 接 6 脚、TXD 接 8 脚、RXD 接 10 脚，115200 8N1），往串口发一帧握手包 `E0 03 00`，板子立马回话了：

```
MMDVM_HS_Hat-v1.4.17 20190529 14.7456MHz ADF7021 FW by CA6JAU GitID #cc451c4
```

能吐出版本，说明板子是活的。至于旁边那块一直黑着的 OLED，顺手查了网表和 `MMDVM_HS` 源码后直接放弃了——它的 SDA、SCL 挂在排针 3 脚和 5 脚上，跟 STM32 一根线都没连，走的是树莓派自己的 I2C，固件里压根一行显示代码都没有。而且 g4klx 新版主分支早就把 OLED 源码删了，x86 电脑既没 `/dev/i2c-1` 也没树莓派 GPIO，不影响通联，黑着就黑着吧。

## Arch 上编 MMDVMHost，连上 BrandMeister

接着拉了 `g4klx/MMDVMHost` 主分支编译，结果 `make` 跑到链接阶段直接炸了：

```
undefined reference to SSL_CTX_get_cert_store@OPENSSL_4.0.0
```

新版合入了 MQTT，要链接系统的 `libmosquitto`。仓库里刚装上的 `libmosquitto 2.1.2` 是按 OpenSSL 4 编的，但我本机还停在 OpenSSL 3.x——太久没滚，撞上经典 Arch 半滚动事故。单升 OpenSSL 会把一堆依赖老版本的包干废，没法偷懒，老老实实 `sudo pacman -Syu` 整机滚一遍重启，回来再编一把过。（顺便一提，主仓库现在只编 `MMDVM-Host`，校频用的 `MMDVMCal` 在另一个独立仓库里。）

改 `MMDVM-Host.ini` 也踩了俩小坑：

- **频点被拒**：最开始随手填了个 `435.000 MHz`，一跑板子直接回 `SET_FREQ NAK`。查了下固件的频带表，435 踩进了 ADF7021 的限制频段，换成 `433.775 MHz` 马上返回 ACK。另外单工板要把 `Duplex=0`，用不到的模式和 CW ID 全关掉，只留 DMR。

- **串口权限**：`/dev/ttyUSB0` 默认属主是 `root:uucp`，普通用户打不开。先拿 `setfacl` 临时放权，代价是每次拔插 USB 都得重新打一遍。

网络这边又编了个 `DMRGateway` 对接 BrandMeister。查了下服务器列表，以前常听说的 4601 在现在的官方清单里已经找不到了（网上有人提的"国服 8601"压根不存在），国内直接连 **BM 4602**（`43.129.83.124:62031`）就行。去 BM Selfcare 后台拿到 Hotspot Security Key 填进 `DMRGateway.ini`，写上呼号 BA4SLT 和 DMR ID，把网关和主程序拉起来：

```bash
cd ~/workspace/DMRGateway && ./DMRGateway DMRGateway.ini &
cd ~/workspace/MMDVMHost && ./MMDVM-Host MMDVM-Host.ini &
```

日志很快刷出了 `Logged into the master successfully`。

## 按下 PTT，开始走弯路

到这步看着好像全通了：板子握手正常、频点 ACK、BM 登录成功。我把 P8260 写好频（433.775 MHz、色码 1、时隙 2、TG 9990），按了一发 PTT。

结果板子灯不闪，日志里一条 RF 帧都没有。拿旁边一台模拟机监听，明明能听到清晰的数传声，说明手台确实在发，问题在板子这边。

接下来大半夜基本全在绕弯子：

1. **先怀疑线材和串口**：CH340 中间断连过好几次，系统日志报 `-32` USB 传输错误，我也跟着怀疑是不是杜邦线接触不良。把配置路径改成了 `/dev/serial/by-path`，又写脚本测载波发射——一开始回 NAK 差点以为板子射频挂了，扒完固件 `SerialPort.cpp` 才发现是测试脚本里模式参数填错了；改成 `STATE_DMRCAL` 后全 ACK，30 秒校准信号发得稳稳的。

2. **再怀疑频偏**：接着开始扫 `RXOffset`，扫到 `-800` 的时候日志突然蹦出来一条 `DMR Slot 2 voice header from 4614415 to TG 9990`，BER 9.7%。当时以为破案了，还顺手总结了两条"经验"：一是晶振偏了 -800Hz，二是手台不能贴脸打，会把板子前端压死，离两三米效果最好。

3. **第二天直接打脸**：把 `RXOffset=-800` 写死进配置，结果第二天开机重启，手台发射又变回彻底零帧。期间还踩了几个小坑——比如发现 DMR 灯灭其实是固件 2 秒无信号自动回 IDLE 的看门狗机制，并不是接收死了；想用 `RSSICAL` 模式直接看信号强度，结果这版固件的 `RSSICAL` 有 bug，一开就把串口流搞乱码；脚本硬杀 `MMDVM-Host` 切频偏还会直接把固件卡死，每次都得拔电重启。

## 真相大白：CH340 带不动，一配置就欠压复位

软件和协议逐字节核对了一遍都没错，最后是用固件自带的 `GET_STATUS`（`0x01`）查模式位才把真凶抓出来的。

板子上电默认 `flags=0x3F`，也就是六个模式全开、轮流扫描。按理说 `MMDVM-Host` 发完 `SET_CONFIG`（只开 DMR）并收到 ACK 后，状态位应该变成单 DMR。但实测下来，发完配置、板子回完 ACK，会诡异地静默大概 0.4 秒——刚好是开机自检闪灯的时间——再一查 `GET_STATUS`，`flags` 又变回了 `0x3F`。

紧接着做了个对照实验：发 `SET_CONFIG`，但把 `modes` 全设成 `0x00`（不触发射频初始化）。这回 ACK 之后 `flags` 稳稳停在 `0x00`，板子没重启。

谜底彻底揭开：**CH340 模块自带的 3.3V 供电电流太小，根本带不动 ADF7021 启动。** 每次主机发配置让射频芯片干活，电压一掉，STM32 直接欠压复位，默默回到默认的六模式扫描状态。DMR 只占六分之一的时间片，所以平时死活收不到；前一天晚上在 `-800Hz` 解出来那一帧，压根不是频偏对了，纯属运气好撞上了时间片。

解法也很粗暴：手边正好有块 ESP32-S3 开发板，直接借它板上那颗 AMS1117 的 3.3V 给热点板 1 脚供电，GND 跟 CH340 共地。换完电源再测 `SET_CONFIG`，板子再也没复位过，`RXOffset` 也老老实实改回了 `0`。

## 丢头帧、差点刷固件、顺手拔错一次线

供电稳住之后，板子确实不再复位了，但马上撞上了另一个更要命的问题：**吞首包头**。

手台每次按 PTT，日志里都能稳稳看到 voice sync，偶尔连结束帧都能解出来，偏偏最关键的第一个 **voice LC header** 死活解不出。而 MMDVMHost 的逻辑很死板，没收到头帧就不会建立通话，后面解出来的语音帧全当垃圾扔掉。

当时怀疑是固件里 ADF7021 的 AGC 在发射爬升瞬间把头帧干废了，连重刷固件的准备都做好了——装上 `arm-none-eabi-gcc`，把 `Config.h` 里的 AGC 改成 `AD7021_GAIN_HIGH` 固定高增益，编出了 `bin/mmdvm_f1.bin`，还查网表确认进 bootloader 要把排针 38 脚（BOOT0）拉到 3.3V，连 `stm32flash` 命令都写好了。

结果还没顾上刷，拿 P8260 试着按了两下，日志突然蹦出两条 `received RF voice header from 4614415 to TG 46025`，通话建起来了，BER 也看着挺漂亮。当时图省事，天真地以为只是刚换完供电头几下没稳住、问题自己好了，就没刷那个改过 AGC 的固件。

中间还顺手闹了个乌龙：后来琢磨着还是试一下 BOOT0 串口刷写流程，结果一通操作完，板子不管是 115200 的正常固件还是 57600 的 bootloader 全无响应，彻底变哑巴。对着排针查了一圈才反应过来——Agent 让我保持 1 脚供电的同时把 38 脚接 3.3V，但我手头就那一根 ESP32 出来的 3.3V 线，直接把 1 脚拔了插到 38 脚上。板子压根没通主电，可不就静默了。插回 1 脚瞬间复活，虚惊一场。

## 9990 回放通了，但根本没法正常用

既然头帧冒出来了，我就接着把 `DMRGateway.ini` 里 9990 的规则补全（默认模板只写了 Slot 1，单工走 Slot 2，手动在 `TypeRewrite` 和 `SrcRewrite` 里补了两行 Slot 2），拿 P8260 切到 TS2 TG9990 喊了一段。等了几秒，手台里清清楚楚传回了我自己的声音，BER 1.3%。

顺手记几个顺带摸出来的 BM 4602 坑：

- **别在本地配 `Options=`**：往 `DMRGateway.ini` 里加 `Options=TS2 46025` 想挂静态组，BM 4602 收到之后直接不回 ACK，网关会无限超时重连。静态组只能去 BM Selfcare 后台配，或者手台 PTT 动态挂。

- **9990 鹦鹉看脸**：4602 公共鹦鹉忙的时候延迟能拉到 20 多秒，甚至发上去二十多帧 DMRD 压根不给回放，不一定都是本地的锅。

- **TG9 没有回声**：中途迷糊了一阵拿 TG9 测回放，折腾半天才反应过来 TG9 本身就没回声功能，测回放老老实实用 9990。

写到这儿，看日志截图、看 1.3% 的 BER、看 9990 跑通，好像已经功德圆满了。

**但实际情况是：这套东西现在基本不能用。**

之前以为"自愈"的吞首包头根本没好。真拿去日常按 PTT，十次里大把都是首包直接被吃掉，板子听见了信号却抓不到头帧，通话压根建不起来，能通完全看脸。加上桌面上电脑屁股后面拖着一块 CH340 再加一块纯当电源用的 ESP32-S3，线稍微碰一下就得重打 `setfacl`、重拉进程，离能用还差十万八千里。

以为到终点了，回头一看其实才刚走到起跑线。下一章就得老老实实回头啃这个吞首包头的硬骨头——不管是真把那个关了 AGC 的固件刷进去、调 P8260 的发射前导，还是接着查这块三无板子的射频毛病，只能继续往深了挖。
